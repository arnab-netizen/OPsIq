## Reconciliation Answers

### 1. Does `owner-mode` exist? — PROVEN
A feature named "owner mode" exists, but it is a **read-only portfolio/admin dashboard**, not a business-recovery loop.

### 2. What exact files implement it? — PROVEN
- `src/domain/owner-mode/owner-dashboard.ts` — enums `HealthStatus`, `ActionQueuePriority`; interfaces `ActionQueueItem`, `ActionQueueSummary`, `KPISummary`, `EngagementHealthSnapshot`, `WorkspaceHealth`, `OwnerDashboardConfig`, `OwnerDashboardView`; validators `validateWorkspaceHealth`, `validateActionQueueSummary`, `validateOwnerDashboardView`. In-memory DTOs only — no Prisma model.
- `src/services/owner-mode/dashboard.service.ts` — pure functions `calculateWorkspaceHealth`, `summarizeActionQueue`, `buildOwnerDashboardView`, error type `DashboardServiceError`. Contains hardcoded synthetic values (`actionCompletionRate: 0.5`, `averageExecutionCertainty: 50`).
- `src/services/owner-dashboard.service.ts` — `getOwnerDashboard` (a **second, overlapping** owner-dashboard service used by the per-engagement dashboard route).
- `src/domain/owner-briefing/` + `src/services/owner-mode/` adjacent owner-briefing engine.
- `src/services/first-value.service.ts` — `getFirstValue` (pilot-proof packet).

### 3. What exact APIs implement it? — PROVEN
- `GET /api/owner/dashboard` (`src/app/api/owner/dashboard/route.ts`) — requires `OWNER_VIEW`; queries real `Engagement`/`Action`/`KPI`/`Recommendation` for the workspace.
- `GET|POST /api/owner/config` (`src/app/api/owner/config/route.ts`) — `OWNER_VIEW`/`OWNER_MANAGE`; **config stored in a module-level in-memory `Map` (line 55), not persisted**.
- `GET /api/owner/first-value` (`src/app/api/owner/first-value/route.ts`).
- `GET /api/engagements/[engagementId]/dashboard` (`getOwnerDashboard`).

### 4. What exact UI pages expose it? — PARTIAL
- `src/app/(authenticated)/owner/first-value/page.tsx` — the **only** owner UI page; renders a `PILOT_PROOF_PACKET` export.
- `GET /api/owner/dashboard` has **no UI page** consuming it (only `src/app/api/internal/owner-dashboard-runtime-proof/route.ts` invokes it as a proof harness).

### 5. Is it in navigation? — FAILED
`src/ui/shell/sidebar-nav.tsx` lists: Dashboard, Decision Check, Leads, Clients, Engagements, Users, Settings, Scenario Lab, Report. **No `/owner` entry.** The first-value page is reachable only by direct URL.

### 6. Is it protected by role/capability? — PROVEN
`withCanonicalEnforcement(..., { requireCapabilities: [OWNER_VIEW|OWNER_MANAGE] })`. `OWNER_VIEW` is granted to `ADMIN_OR_PORTFOLIO_MANAGER` and `SYSTEM_ADMIN` (`src/policies/capability-check.ts:9,71`). `OWNER_MANAGE` → `SYSTEM_ADMIN` only. The business-owner role `CLIENT_OWNER` does **not** have `OWNER_VIEW`.

### 7. Is it workspace-isolated? — PROVEN
All queries scope by `verifiedWorkspaceId` (e.g. `db.engagement.findMany({ where: { workspaceId } })`), plus `enforceWorkspaceScoping` in config route.

### 8. Does it intake real business data? — NOT PROVEN
Owner-mode has **no intake**. It is read-only aggregation. The only system intake is the generic `/diagnosis` form (3 optional numbers: `monthlyRevenue`, `monthlyCosts`, `customerCount`).

### 9. Does it persist real business data? — PARTIAL
It **reads** persisted `Engagement`/`Action`/`KPI`/`Recommendation`. Its own owner config is **not** persisted (in-memory `Map`). No owner-business or metric model exists.

### 10. Does it calculate real metrics? — FAILED
`calculateWorkspaceHealth` derives engagement counts but injects hardcoded `actionCompletionRate: 0.5` and `averageExecutionCertainty: 50`. No business metric (margin, repeat rate, complaint rate, turnaround, etc.) is computed.

### 11. Does it generate diagnosis? — NOT PROVEN (in owner-mode)
Diagnosis lives in `src/services/diagnosis.ts` (separate). Owner-mode merely surfaces resulting `Recommendation` rows.

### 12. Does it generate evidence-backed findings? — FAILED
The diagnosis path it surfaces creates Evidence by restating the finding (`diagnosis.ts:716-728`); no source metric/threshold/baseline. Owner-mode adds nothing here.

### 13. Does it generate recovery actions? — NOT PROVEN (in owner-mode)
Actions are generated by the diagnosis flow, not owner-mode.

### 14. Does it assign actions? — FAILED
Diagnosis persists `Action.assignedTo: null`, `dueAt: null`, `status: "draft"` (`diagnosis.ts:792-805`). No assignment endpoint exists. Owner-mode cannot assign.

### 15. Does it track execution? — FAILED
The action item PATCH route enum `["open","in_progress","completed","blocked","deferred"]` (`actions/[actionId]/route.ts:16`) does not match `ACTION_STATUSES ["draft","assigned","in_progress","blocked","completed","verified","cancelled","overdue"]` (`statuses.ts:43`). A diagnosis `draft` action cannot be advanced. The route also filters a non-existent `Action.workspaceId` column.

### 16. Does it verify before/after outcomes? — FAILED
`verifyOutcomeValue` is hardcoded to `confidence: 0`, `verificationMethod: "customer_reported_unverified"` (`src/services/outcome/verification.ts:51-58`; asserted by test). No before/after real-metric comparison anywhere.

### 17. Does it support repeated cycles? — NOT PROVEN
Each diagnosis creates a new `Engagement` (`code: "DIAG-"+Date.now()`). No cycle linkage or comparison.

### 18. Can it be used by the owner on Tumbledry today? — NO, NOT PROVEN
No business setup, no laundry metric intake, no real calculation, no assignment, no verification.

### 19. What parts should be reused? — PROVEN reusable primitives
- Capabilities `OWNER_VIEW` / `OWNER_MANAGE` and the role→capability map (`capability-check.ts`).
- Route enforcement `withCanonicalEnforcement` (auth + workspace + capability + audit) — `src/lib/canonical-route-enforcement.ts`.
- `db` Proxy (`src/lib/db.ts`), `emitAuditEvent` (`src/infra/audit.ts`), `parseRequestBody`/`parseOrThrow`/`uuidSchema` (`src/lib/validation.ts`), `canonicalJson` (`src/lib/canonical-json-response.ts`).
- Health-status vocabulary (`HealthStatus`) and the dashboard composition pattern from `owner-mode/dashboard.service.ts`.
- Sidebar nav pattern (`src/ui/shell/sidebar-nav.tsx`) and authenticated layout/shell.

### 20. What parts should be repaired? — PROVEN
- The duplicate owner-dashboard services should eventually be reconciled (out of scope here; do not regress them).
- Owner config persistence (in-memory → DB) — not required for the recovery loop; left as-is.

### 21. What parts should be replaced/bypassed? — PROVEN
- The broken `Action` status enum + assignment route, and the hardcoded `outcome/verification.ts` — these are **structurally unusable** for the recovery loop. The recovery mode must **not** build on them; it needs its own action + verification models with a correct status machine and real before/after comparison.

---

## Summary Verdict

`owner-mode` exists and provides **reusable cross-cutting primitives** (capability gating, canonical enforcement, db/audit/validation, health vocabulary, dashboard pattern) but is, as a feature, a **portfolio/admin read-only dashboard**: no intake, no real metric calculation, no diagnosis of its own, broken assignment/verification, no cycles. It is therefore **structurally useful but functionally incomplete** for the founder's end-to-end real-business recovery requirement.

This directly informs the Phase 1 decision: reuse the primitives, do **not** extend the broken portfolio dashboard data model, and create a clearly-named recovery surface with its own correct data model.
