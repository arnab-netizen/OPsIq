## 3. Canonical survivor and why

**Survivor: Owner Intelligence Spine (contract + arbitration) + Owner Home aggregation.**

- **All eight domains in one contract.** It is the only path that normalizes all 8 domains into one contract (`OwnerAction`) using per-domain adapters (`business-condition.service.ts:48-338`, reused by `home.service.ts:207-307`). It is also the only path that filters to open work (summary.ts:164).
- **Now View cannot be the survivor.** It reads **no** domain action or finding table (only categorical cycle states, `owner-now-view.service.ts:876-877`). Its ladder has compliance below profit leak (`issue-priority.ts:39-50`). Electing it would lose every domain decision.
- **`topRoute` cannot be the survivor.** It is computed live from workspace-level signals, is ambiguous across businesses (`owner-now-view.service.ts:2140-2145`), and is not persisted until an owner starts work.
- **Business Condition's rollup is a strict duplicate** of Home with a weaker filter.

## 4. Priority-score hostile audit

- **Saturation.** The raw product reaches 300, so any combination with impact × confidence ≥ ~50 and high urgency or severity saturates at 100. Example: Strategy funding gap, investment ₹60,000 vs cash ₹10,000, computes 143 → 100.
- **Tie semantics.** After saturation, the order is decided by `findingCode` string order: e.g. `"FIN_…" < "STR_…"`, so Finance always wins a saturated tie against Strategy for alphabetical reasons.
- **Severity is invisible at arbitration.** Only the stored `priorityScore` is ranked, and severity is dropped by every adapter.
- **Cross-domain incomparability.** Recovery uses a fixed lookup scale and never reaches 100. The "survival" multiplier means a different risk score per domain.

**Existing documented precedence (reused, not invented):**
- `docs/real-world-data/worst-case-survival-recovery-proof/CRISIS_PRIVACY_AND_SAFETY_NOTES.md:8`: "Cash/continuity, customer/reputation, quality, legal/contract/tender, and capacity always outrank growth/marketing".
- Category-first, then severity, as in `issue-priority.ts:108-117`.
- `SURVIVAL_DOMAINS` in `contracts.ts:36`.
- The mission's required precedence puts safety/compliance first, consistent with the CRISIS rule that these classes outrank growth.

**Canonical order (implemented in PR A):**

1. `SAFETY_COMPLIANCE`
2. `SURVIVAL_CASH`
3. `CUSTOMER_SERVICE_FAILURE`
4. `OVERLOAD_BLOCKING`
5. `PROFIT_LOSS`
6. `BLOCKED_EXECUTION`
7. `PLAN_COMMITMENT_RISK` — a plan being evaluated that would put money or delivery at risk if committed now (assigned only from Strategy's resolved decision)
8. `MISSING_CRITICAL_EVIDENCE`
9. `GROWTH_OPPORTUNITY`
10. `PROCESS_OPTIMISATION`

Classification is by finding code, from a total table covering every code the domain rule files emit. An exhaustiveness test enforces it. Codes are classed by the business harm they describe, not by their domain: e.g. `OPS_CAPACITY_BOTTLENECK` is overload, `OPS_HIGH_DELAY`/`SALES_WEAK_REPEAT` are customer failure, loss/cash-leak opportunities are profit loss, `FIN_HIGH_PAYABLES` is survival cash.

**Source-specific classes (never fabricated):**
- **Strategy** is classed from its RESOLVED five-state decision (`NEED_INFO`/`DONT_AS_PLANNED`/`NOT_YET`/`GO_WITH_CONDITIONS`/`GO`) and the actual blocker (`strategyCandidatePriorityClass`): under `NOT_YET`/`DONT_AS_PLANNED` a money-at-risk blocker (unaffordable, low reserve, negative case/ROI, weak ROI, long payback) or high execution risk is `PLAN_COMMITMENT_RISK` — above optional growth and data requests, below every PRESENT problem (the harm happens only if the owner commits; the "don't commit yet" warning is always in `whatNotToDo`). Every other Strategy step, and all positive upside, is `GROWTH_OPPORTUNITY`.
- **Compliance** uses the existing compliance/action-gate semantics only: a hard block (`breached`, or `active` and expired — the gate's hard stop) is `SAFETY_COMPLIANCE`; an expired item already in evidence/review is `BLOCKED_EXECUTION` (`COMPLIANCE_RENEWAL_IN_PROGRESS`). Severity is set only where the compliance service itself raises a critical alert (`breached`); priority score and impact are 0 (none exist in the model); confidence comes from the item's recorded provenance. Upcoming/non-blocking items are not candidates. This reorders compliance relative to the old Now View ladder (which put it below profit leak) — deliberately, per the CRISIS precedence above.
- **Business risks** (workspace-level) are candidates only when the workspace has exactly one real business, fixture rows and fixture-tainted startup sessions excluded; mitigating risks use residual risk; confidence is the fixed owner-recorded value 0.6.

Within a class the order is:
0. a RECORDED compliance block (a breach, or an active expired obligation the action gate stops on) before estimates and diagnosed actions
1. severity
1a. CURRENT evidence before an evidence refresh: a refresh target exists because OpsIQ no longer trusts the stale diagnosis enough to act on it, so it never defeats a fresh, evidence-backed danger of equal class and severity (restored from the linked finding; Recovery from its `priority`)
2. `priorityScore` (the existing spine score)
3. expected impact
4. confidence
5. lower effort

Stable id and code are used only as final deterministic tie-breakers.

## 5. Terminal and stale handling (canonical eligibility)

A candidate is excluded from the election when any of these holds:
- its status is `completed` or `cancelled`, or any other non-open status (`superseded`);
- its latest CONCLUSIVE own verification (`verified_improved` / `verified_not_improved`; later inconclusive rows do not reopen it) reached a directional (`up`/`down`) target (`extractReachedTargetFromVerification`, `owner-finance/outcome-signals.ts:112`) AND was recorded at or after the evidence its cycle rests on → `verified_complete` (a verification carried forward from before newer evidence never closes the action against it; with no known evidence time nothing is shown to be causal, so the action stays open);
- a verification of the same finding in that domain reached its target at or after the cycle's evidence was captured → `verified_fix_awaiting_new_evidence` (the fix waits for new figures before the finding can be raised again);
- it is not on its domain's current diagnosis cycle. Engaged actions whose finding is still raised are re-attached to the new cycle by the diagnosis (`planWithContinuity`, `src/domain/founder-recovery/action-continuity.ts`), so an older-cycle action is one current evidence no longer raises;
- it is a Strategy action that is incoherent with the live decision (`coherentStrategyActions`);
- it is a survival-class Cash or Finance action whose unsafe reading was superseded by a NEWER, disagreeing reading of the other source (`currentCashFinanceReading`, `src/services/owner-spine/current-cash-finance-reading.ts` — the ONE current cash/finance reading that Home, Now View, the owner action gate and `/api/owner/dashboard` health all use; Formal Consulting Mode's recommendation cash gate keeps its own pre-consolidation worst-of semantics, §5c). Home applies exactly the shared reading's supersession — the same effective-evidence eligibility the action gate enforces. What DRIVES the enforced state (the reading's `gateDriver`: cash, a Finance survival state driven by profit/margin per Finance's own findings `financeSurvivalDriver`, or figures that are not current) names the blocker; it never changes which reading is current. "Newer" is the evidence PERIOD each reading describes (its snapshot's `periodEnd`), never the cycle's `createdAt` — a re-diagnosis from an old snapshot after an action is completed/verified must not look current. Incomparable freshness (equal or missing periods) excludes nothing.

**The current diagnosis cycle** of a domain is the diagnosis of its latest evidence PERIOD, then the latest capture of that period, then the latest run on it (`CURRENT_DIAGNOSIS_CYCLE_ORDER` / `CURRENT_RECOVERY_CYCLE_ORDER`, `src/services/owner-spine/current-diagnosis-cycle.ts`) — never merely the highest sequence number: a back-filled OLDER period diagnosed later is history, not the current reading. Strategy is the one exception: its snapshots are saved scenarios, so its current evaluation is the scenario evaluated last (`CURRENT_STRATEGY_CYCLE_ORDER`). Every current-cycle read (the candidate builder, domain dashboards, Business Condition, change facts, Now View, both cash gates, progress, the dashboard route, re-diagnosis targets) uses these orders; `src/__tests__/governance/current-diagnosis-cycle.test.ts` fails any other ordered cycle read except the listed write-path reads (next sequence number, a diagnosis's own drift baseline) and cycle-history lists (display order, never a current-state selector); `cash-finance-parity.db.test.ts` proves the order is semantic — the later-period, later-run diagnosis stays current for the dashboard, Home, Business Condition, Now View and the gate even when its `createdAt` is older (mutation-checked: a `createdAt` order fails it).

**The current cash/finance reading.** A Finance diagnosis whose snapshot the owner has since amended is not a current reading (never passes as SAFE); its state is kept as the last known Finance state until the amended figures are diagnosed. An incomparable disagreement is an explicit conflict — the Home cash card reads "Cash and Finance signals currently disagree … Confirm the latest figures before relying on the survival assessment." with no level or score; Now View raises it — never resolved by picking one side. Gates enforce `gateState`: the arbitrated state, the worse of the two when they conflict, and never safer than an amended-but-undiagnosed unsafe Finance reading.

**Stale evidence** (evidence period older than 45 days, a period ending AFTER now — future-dated figures are never current evidence: every current-cycle and current-snapshot reader filters to periods that have ended by `now` (`currentEvidenceWhere`, `current-diagnosis-cycle.ts`; the financial snapshot selector likewise), so a future period can neither hide the present one nor win the cash/Finance arbitration; the decision says "… figures entered for a period that has not ended yet are not used — OpsIQ advises on the latest period that has ended", never "out of date" — or a Finance snapshot amended after diagnosis) never lets an old high-class item win: the stale domain's actions are excluded as `stale_evidence` and replaced by ONE explicit `evidence_refresh` target per stale domain, which takes its class, severity, priority, impact and effort from the ONE most serious item it stands in for (never a worse severity borrowed from another class), with confidence capped at 0.4 (out-of-date figures never read as high confidence). It names the stale items. The comparator ranks current evidence ahead of a refresh target of the same class and severity (`current_evidence`), so a stale refresh never outranks a fresh same-class danger. On every surface a refresh target is presented as a data request: its severity reads "last flagged", its reasons say the figures are out of date, and presentation guardrails (control center, Now View avoid list) are never rewritten around it. Recovery staleness is age-only (Recovery snapshots have no amendment chain). Ageing never "resolves" a critical issue in "what changed": stale critical issues stay open and the owner is told the figures are out of date. Current hard safety/compliance items are not domain actions and are unaffected.

**Finance missing data** comes from the EXACT snapshot attached to the latest Finance cycle (`finance.snapshot`) — in Home, Business Condition and the Finance dashboard — never from whichever snapshot has the latest period.

**Survival issues are separate from their actions (`survival_reading`).** A `SURVIVAL_CASH`-class finding raised by a cash/finance diagnosis is an open business ISSUE for as long as the evidence that raised it is the evidence OpsIQ holds; an action is only how the owner responds (`survivalIssueCandidates`, owner-decision-candidates.ts). Per stable issue identity (domain + finding code): an eligible action for the SAME issue represents it (no duplicate issue + action candidate); a completed, cancelled, superseded or VERIFIED action for it — or none at all — does not make it go away: the action closes, the issue stays a candidate carrying that action's title and status and asks for refreshed figures. Action lifecycle is not issue lifecycle: the issue stops competing only when newer trusted evidence no longer raises it, or when a verification directly MEASURED the issue's own metric (the finding's `sourceMetric`) after the issue's evidence time (`verificationResolvesIssue`). Every domain's verification service records the after value the owner entered (`afterValue: input.afterValue`), so no current domain's verification is a direct measurement — in practice only newer evidence clears a survival issue, and a carried-forward historical verification can never clear a newly raised one. **Scope:** this issue-over-action rule covers survival (`SURVIVAL_CASH`) issues — the P1 scope. For other classes the accepted action-lifecycle semantics stand unchanged (a fix verified after the evidence keeps a re-proposal from the same snapshot out until new figures arrive — the earlier "verified Minor Finance item" production fix); that is a deliberate boundary, not an oversight; a reading superseded by a newer disagreeing reading of the other source raises nothing; a stale reading raises the issue as stale, so the arbiter turns it into an explicit refresh target (never high-confidence growth). An open action for a DIFFERENT survival finding (e.g. medium `FIN_HIGH_PAYABLES`) never hides another (e.g. critical `FIN_INSOLVENT_RUNWAY`). The issue's wording comes from its own finding, never a generic "cash position" claim; a survival state driven only by non-survival findings raises nothing. Regressions: `survival-reading-candidate.test.ts` (A–F), `owner-decision-consolidation.db.test.ts`.

## 5a. "What changed" — from persisted mutation facts; reads never write

Reading the owner decision performs no writes: `getOwnerHome()` (and therefore `/api/owner/home`, the Command Center, the control center and Portfolio) emits no audit event, takes no lock and records no decision memory. Every owner read surface — the seven domain dashboards, the Control Center, Priorities' feeds (`/api/owner/risks`, `/api/owner/alerts`, `/api/owner/priorities`), the Portfolio dashboard and Home — sends zero write statements, and AuditEvent, cycles, actions, snapshots, do-not-repeat memory and compliance/risk records are unchanged after all of them (fingerprinted). `/api/owner/now-view` writes no decision memory, audit event or alert; its only write is Now View's own pre-existing guidance-history row, now appended only when the observed state differs from the latest recorded one — a repeat or concurrent read of an unchanged business writes nothing. Overdue risk-review alerts are raised by the scheduler's risk-review scan (`enqueueDueRiskReviewScanTasks` → `risk-review-scan` → `scanOverdueRiskAlertsForWorkspace`) and by the risk review mutation, never by a read (the former fire-and-forget on every Now View load is removed) (`owner-decision-read-only.db.test.ts` captures every SQL statement at the node-postgres boundary). The earlier read-time `owner.decision_changed` memory is removed; no schema or table is added. "What changed" (`describeOwnerChanges`, over `OwnerChangeFacts` gathered read-only by `owner-home/owner-change-facts.ts`) is built only from what was persisted when something happened, within a 14-day window shown on the card ("Recent changes (last 14 days)"):
- **New evidence** — per EVIDENCE domain (Strategy evaluates hypothetical plans: a scenario switch or re-evaluation is never "new figures" and never shows an issue appeared or resolved), dated by evidence chronology, never by insertion or re-diagnosis time: the transition's time is when the current evidence (snapshot) was FIRST diagnosed — re-running the engine on the same figures never re-dates it into the window — and its baseline is the current diagnosis (same order) of the evidence that was AVAILABLE before that (cycles created before the current evidence's first diagnosis, on a different, non-future snapshot), so a back-filled older period entered afterwards is never the baseline and cannot produce a false appeared/resolved/worsened/improved line; future-dated current figures report nothing. Changes are reported only when the current figures are causally newer: a later evidence PERIOD, or the same period captured later (a correction). A back-filled older period diagnosed afterwards is history, never "new" (`EVIDENCE_UPDATED`). A re-diagnosis of the same snapshot is not new evidence. On newer evidence: a critical issue not raised before → `CRITICAL_ISSUE_APPEARED`; severity up/down → `SEVERITY_INCREASED` / `SEVERITY_DECREASED` (still open); a previously critical issue that the NEWER figures no longer raise → `CRITICAL_ISSUE_RESOLVED`. The same issue still raised by new evidence is an evidence update, never "resolved". Only CURRENT EFFECTIVE evidence reports change: figures older than the freshness window, or Finance figures the owner has since amended, report nothing, and an amended Finance version is never the baseline. Issue identity is the business LEVER where a code has one (`ownerLeverKey`, e.g. every runway tier is `cash_runway`), so a tier change is one issue changing severity — never "resolved" plus "new". A diagnosis that could not measure (it raised a `*_MISSING_CRITICAL_DATA` finding) never reports an earlier issue as resolved: a data gap is not a fix. Evidence "going out of date" uses the builder's own boundary and never applies to Strategy scenarios.
- **Record lifecycle** — from the records' own audit trail, confirmed against each record's CURRENT state: a risk identified at critical severity; resolved/closed only while its record is still closed (a reopened risk is open); accepted (review workflow) reported as accepted — `RISK_ACCEPTED`, never as resolved; mitigated below critical only on a proven transition in that event (status moved to MITIGATING or its residual risk dropped below critical — from an edit or a review) and only while it still is; a compliance breach recorded; a breach closed only when cleared to an in-force or waived status that the record still holds and the item raises nothing now ("evidence pending"/"review pending" is remediation, not closure; an expired item cleared to "active" is still a hard stop). QA fixture risks (flagged, or linked to a fixture-tainted startup session) never count. Nothing is inferred from absence.
- **Completion / verification** — completed actions and target-reached verifications.
- **Attribution** — judged against who was active just before the change: lost when this business existed alone and another real business was added inside the window; regained when a real business that was active alongside it was archived inside the window (proven by that business's own audited `isActiveChange` from active to archived — a repeated no-op request records no change and is never read as an archival). Only when open critical workspace-level issues exist → `ATTRIBUTION_CHANGED`; never an open/resolved claim.
- **Out of date** — evidence whose period passed the freshness limit inside the window.
Lines are ordered by importance (record lifecycle, attribution, issue changes, completions/verifications, out-of-date evidence, then which domains got new figures) and de-duplicated, so a short list never hides a lifecycle change. "Main target changed from X to Y" is not reported: it cannot be reconstructed truthfully from persisted facts without read-time persistence.

## 5b. Surfaces that are explicitly subordinate or domain-local

- Home, Cockpit, Priorities, Command Center and the `/owner/now` headline/plain-language block all render the one `CurrentOwnerDecision`.
- **Only `CurrentOwnerDecision` issues overall-business imperatives.** Every other system's "do not / stop / blocked" is a constraint that passes through ONE reconciler before it is shown beside the decision (`reconcileOwnerProhibition`, `src/domain/owner-spine/owner-imperatives.ts`). Whether a prohibition touches the target is decided by two pure, fixed semantics — never the domain name: `ownerTargetIntent` (SAFETY / STABILISE / REPAIR / EVIDENCE / EXECUTE / GROW, from the canonical class with rule-cited code overrides; a Sales/Marketing repair such as `MKT_WASTED_SPEND` or `SALES_HIGH_COMPLAINT_RATIO` is REPAIR, not growth) and `ownerLeverKey` (findings share a lever only when their rule definitions measure the same source metric, enforced against the rule files by `owner-imperatives.test.ts`). A prohibition that would veto the main target or a supporting step (growth rules vs a genuine GROW target, a workload rule vs any action target, a same-lever item) becomes a condition on executing it; a refresh main target rewrites nothing.

## 5d. Evidence continuity and write concurrency (Round 7)

- **Back-fill never takes over in-flight work.** A diagnosis of an OLDER period is historical: an engaged action attached to a cycle of a NEWER period is "held" (`planWithContinuity(…, periods)`) — neither re-attached to the historical cycle nor duplicated on it. A newer period carries it as before (all six evidence domains and Recovery).
- **Recovery's trend baseline** is the previous evidence PERIOD (the latest cycle whose period ended before this snapshot's, and has ended at all), never the largest run number; cycle numbers still record run order.
- **Re-diagnosis targets** (after a completion or verification) are the latest period that has ENDED.
- **Action transitions are compare-and-set** in all nine action services (`applyGuardedActionUpdate`: id + workspace + the status validated, plus `version` for Recovery; exactly one row): an identical concurrent submission is idempotent (no second audit, outcome or re-diagnosis), a conflicting one is a 409. The gate runs after the request's own validation. Compliance status transitions and risk updates/reviews are compare-and-set too (risk: on the row version, covering likelihood/impact/residual/status; a status change follows the review lifecycle).
- **Strategy's held step.** A plan step the owner action gate holds back is shown as held — "This step is currently held by <constraint>. <Clear/verify the condition> before proceeding." — never as done, verified or "add it to your action list"; an open step is described as "in your action list" only when it is an action row.
- **Command Center** clears the previous business's data at the start of every load (a business switch never shows another business's main target or plan action), and the plan action title goes through the plan-analysis reconciler.
- **Plan-analysis softening** removes ordering words only from owner-directed imperatives (an ordering lead or an opening imperative verb); descriptive sentences are left exactly as written.
