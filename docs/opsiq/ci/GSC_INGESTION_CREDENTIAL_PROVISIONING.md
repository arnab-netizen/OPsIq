# GSC ingestion credential provisioning (runbook and threat assessment)

Workflow: `.github/workflows/provision-gsc-ingestion-credential.yml` (dispatch-only, `production-operator`, main-only).
Script: `scripts/gsc-provision/provision.ts`. Audit: `scripts/gsc-provision/audit.sql`.
Target (exact, verified inside the database before any write): Neon project `patient-lake-61323111`, branch
`br-purple-boat-ayjn6zl6`, endpoint `ep-empty-sky-ay1e6c27`, database `neondb`. Role `opsiq_gsc_ingestion`;
table `public.search_console_metrics`; GitHub environment `gsc-ingestion`; secret `GSC_INGESTION_DATABASE_URL`.

## Why this shape
- Neon's control plane accepts only **plaintext** passwords in `CREATE/ALTER ROLE ... PASSWORD`; it rejects a SCRAM verifier.
  So the password must be generated by a trusted process that also holds the privileged connection. That process is this
  protected workflow: the password is generated in memory (CSPRNG, 256 bits), used in exactly one SQL statement over verified
  TLS, and never printed, never an argument/input/expression, never in an error (`sanitizeError`).
- GitHub's `GITHUB_TOKEN` cannot write environment secrets and no PAT is created, so the connection string leaves the process
  **only as a libsodium sealed box** to the exact `gsc-ingestion` environment public key. The sealed JSON is handed back and
  stored through the already-connected Composio action `GITHUB_CREATE_OR_UPDATE_AN_ENVIRONMENT_SECRET` (Composio never sees plaintext).

## Procedure (each step is its own approved dispatch)
1. `DRY_RUN` - read-only identity/capability/role-presence check. 2. Fetch the env public key + `key_id` (Composio, public).
3. `CREATE` (phrase `CREATE GSC INGESTION ROLE`) - creates the role **NOLOGIN**, grants exactly SELECT/INSERT/UPDATE on the one table
   and CONNECT, audits effective privileges, seals, uploads the sealed file. 4. Store the sealed value as the environment secret and verify its metadata
   (name + timestamps; the value is never readable). 5. `ACTIVATE` (phrase `ACTIVATE GSC INGESTION ROLE`) - re-audits, enables LOGIN, re-audits, and restores
   NOLOGIN on any failure. 6. Dispatch `scheduled-gsc-ingestion.yml`; its own credential preflight re-verifies least privilege.

## Recovery (no orphaned active login)
The role stays `NOLOGIN` until ACTIVATE, so a failed transfer can never leave a usable credential. If the secret was not stored, run
`RECOVER_NOLOGIN` (phrase `RECOVER GSC INGESTION ROLE`): allowed only for an existing NOLOGIN role; it sets a fresh password, re-audits and re-seals.
`CREATE` refuses an existing role; nothing deletes a role or resets a LOGIN role's password.

## Effective-privilege audit (fail closed)
Evaluated with `has_*_privilege(<role>, ...)` so inherited, PUBLIC and column-level access count: no elevated attribute, connection limit exactly 2,
no memberships / SET ROLE / members, owns nothing, CONNECT yes, database/schema CREATE no, schema USAGE yes, exactly SELECT+INSERT+UPDATE on the
target and nothing else on it, zero access (table or column) to any other relation, zero sequence access, zero executable SECURITY DEFINER functions,
`idle_in_transaction_session_timeout=60s`. PUBLIC privileges and other roles are never modified.

## Threat assessment of the sealed-ciphertext hand-off (EXCEPTION REQUIRED before use)
The only GitHub-supported way to move the sealed value out of a runner without a token is a workflow artifact; the repository is public, so the artifact is
readable by any signed-in GitHub user while retained.
| Risk | Assessment | Control |
|---|---|---|
| Confidentiality | The artifact holds only a sealed box to GitHub's environment key; only GitHub's private key opens it. No plaintext password or URL exists in it. | libsodium `crypto_box_seal`, exact key/`key_id` |
| Outer encryption to a second ephemeral key | Adds no confidentiality (inner box already opaque to everyone but GitHub) and needs private-key handling and a download path. Not used. | n/a |
| Authenticity / substitution | A sealed box has no sender authentication. An attacker cannot add an artifact to a run without workflow write access, and the file embeds `run_id`, commit SHA and `key_id`, all checked against the dispatched run before use. Writing a stranger's ciphertext into the secret cannot succeed for the attacker (no write access) and would only break ingestion (fails the credential preflight, fail closed). | run correlation, `retention-days: 1`, `overwrite: false` |
| Replay | A stale artifact fails: key rotation changes `key_id`; the role password is replaced on RECOVER; ACTIVATE re-audits. | single use, 1-day retention |
| Cleanup | Runner copy removed in an `always()` step; the artifact expires in 1 day and is deleted after the secret is stored. | `rm -f`, retention |
| Recovery after failed transfer | Role is NOLOGIN; RECOVER_NOLOGIN re-seals with a fresh password. | see Recovery |
| Residual | The plaintext password exists transiently in the memory of one runner process and in one SQL statement sent over TLS; Postgres server logs record it only if that statement itself errors (it is a server-side, non-public log). | accepted, documented |
Requested exception: use the sealed-ciphertext artifact above, for CREATE/RECOVER_NOLOGIN only.

## Not covered / limitations
- Neon-specific behaviour (staged `ALTER ROLE ... LOGIN`, `CREATE ROLE` outside a transaction, `pg_auth_members.set_option`) is proven on PostgreSQL 16 only; the first `DRY_RUN`
  and `CREATE` against production exercise it, and every failure leaves the role NOLOGIN.
- The workflow's concurrency group is its own; it does not share a group with `migrate-production` / `reconcile-runtime-role` (changing those is out of scope). A Postgres advisory lock serialises role operations within this workflow only.
- Operator capability (CREATEROLE + owner of the target) is verified at run time by `DRY_RUN`; it was verified for the equivalent `neondb_owner` identity, not for the secret itself.
