# QuickBooks Online — READ-ONLY synchronization (V26 / V26A hardening)

*Status labels (documentation only, not code identifiers):* QBO_READ_ONLY · NO_QBO_WRITE_API · PRODUCTION_MIGRATION_REQUIRED=YES (`20261010090000_qbo_read_only_sync_persistence`, additive) · NO_EVIDENCE_ADOPTION · `WEBHOOK_INTUIT_CONFIGURED=NO` · `LIVE_QBO_CALL_EXECUTED=NO`

Builds on the reviewed OAuth + persistence foundation (`QBO_CONNECTION_PERSISTENCE.md`). Adds the first read-only sync, a manual owner trigger, a token-free status API, a scheduled sync, and a signature-verified webhook that is only an event *hint*.

## 1. Source audit — answers to the Phase 1 questions

| Question | Answer (source of truth) |
| --- | --- |
| How is an ACTIVE connection resolved business-safely? | `resolveSyncableConnection({workspaceId, businessId, connectionId})` in `qbo-sync-store.service.ts` selects by the full triple; a connection of another workspace/business is indistinguishable from a missing one. Status must be `ACTIVE`, business active and non-fixture, and `connection.environment` must equal the configured environment. The scheduler/webhook entry recovers the business from the connection row by (claimed workspace, connection id) only. |
| How are encrypted tokens loaded? | `loadQboTokensForUse` (`qbo-connection.service.ts`) — server-side only, `decryptOAuthToken` with the workspace-bound key. `getUsableQboAccessToken` is the only caller on the sync path; the plaintext never leaves the process (not in outcomes, audit payloads, logs or errors). |
| How does refresh happen? | `getUsableQboAccessToken` refreshes only when the access token has < 2 minutes left (or once per sync after an API 401) via `refreshQboTokens`; never retried inside the service (a lost response may already have rotated the token). |
| How do CAS/revision prevent stale refresh writers? | Refreshers of one connection are first serialized by a short DB claim (`qbo_sync_states.refresh_claim_*`, no open transaction), so Intuit — which ROTATES the refresh token — is called once; a waiter re-reads the stored tokens instead of refreshing again. The grant is then persisted with `rotateQboTokens({expectedRevision})` — a conditional UPDATE on `revision` (retried on transient DB errors with the same grant); `STALE_REVISION` ⇒ the loser discards its grant and adopts the stored one. A forced refresh (after an API 401) names the revision that was rejected and is a no-op if a newer revision is stored. |
| How do scheduled jobs obtain workspace/business? | `ScheduledTask.workspaceId` is set at enqueue and handed to the handler as `context.workspaceId` (never from payload). The payload carries only `connectionId`; the business comes from the connection row. |
| How is external-source data stored with provenance? | The generic `External*` tables are not tenant-/realm-aware (same reason as `QBO_SPECIFIC` in the persistence doc), so sync data lives in QBO-specific mirror tables keyed by connection, with run ids, provider timestamps/SyncToken, content hashes and fetch times. |
| Which owner-facing records can safely receive QBO data? | **None in this slice.** `OwnerFinancialSnapshot`/`OwnerCashflowSnapshot` are owner-attested; QuickBooks values are held as provider observations and adopted only through `resolveFinancialFieldPrecedence` (§7) in a later reviewed slice. |

## 2. Supported sources (derived, not assumed)

`SUPPORTED_QBO_READ_ENTITIES = CompanyInfo, Customer, Invoice, Bill, ProfitAndLoss(report), BalanceSheet(report), AgedReceivables(report), AgedPayables(report)`

Derived from the fields OpsIQ's finance/cashflow snapshots consume (table in `qbo-sync-model.ts`): revenue/COGS ← ProfitAndLoss; cash ← BalanceSheet `BankAccounts`; receivables/payables ← BalanceSheet and the aged reports (both are read and stored; **no reconciliation between them is implemented** — only the balance equation, gross profit and aging sums are checked, see §9); overdue ← aged reports (every non-"Current" bucket); customer/order counts ← Customer, Invoice; payables detail ← Bill. Deliberately **not** synced: Vendor, Account, Payment, Purchase, CashFlow, TrialBalance, payroll and everything else in the read catalog. Adding a source is a reviewed change to `qbo-sync-model.ts` **and** to `qbo-foundation-boundaries.test.ts`.

Every provider request goes through `createQboReadClient` (GET-only). The sync service calls exactly `companyInfo`, `query`, `count`, `readEntity` and `report` (all GET).

## 4. Lease, idempotency, resumption

* **One lease per connection**: acquisition is one conditional `UPDATE … WHERE lease_token IS NULL OR lease_expires_at <= now` inside the same transaction that records the `RUNNING` run; the loser gets a typed `BUSY` (HTTP 409) and nothing runs. TTL 15 minutes (above the worst-case retry budget of one provider request) and extended **before every provider call** and by every persisted page.
* **Stale workers cannot write**: every persisted page/report re-verifies *and extends* the lease in its own transaction; finishing releases it with a CAS. The fence is the **(token, epoch)** pair — a takeover replaces the token, so a taken-over worker always fails with `QboLeaseLostError`; an expired-but-untaken lease can still be finished by its owner (work is not discarded when nobody competed). The abandoned run is marked `ABANDONED` and audited.
* **Idempotency keys** carry the lease epoch: MANUAL `manual:<requestId>`; SCHEDULED `scheduled:<UTC day>:<epoch>`; WEBHOOK `webhook:<15-min index>:<epoch>` (run key) — the webhook TASK key is separate: `qbo-read-sync:webhook:<connection>:<epoch>:<6-hour bucket>`. Two triggers racing from the same state collide on the unique key and replay; a retry after a failed / abandoned / crashed attempt (epoch moved on) runs under a fresh key, so a failure never "swallows" the day. Same-day repeat of a *successful* scheduled sync is `NOT_DUE`; a webhook-triggered run happens only while an unserved hint exists. A non-successful replay is never reported as success (HTTP 409).
* **MANUAL cooldown**: 60 s per connection (each run costs ~11 provider calls).
* **Bounded work per execution, durable checkpoint, no cap on total dataset size (one fail-closed exception for a single oversized equal-timestamp bucket: see §9).** One execution stops starting new steps once `QBO_SYNC_PAGES_PER_EXECUTION` (100) provider calls (pages, `count(*)` probes and by-id verification reads) are spent; the budget is checked between steps, so the step in progress can add a few calls, and the wall-clock deadline below is the hard bound. When the budget is spent before exhaustion is *established*, the run ends `PARTIAL` (outcome `CONTINUING`, HTTP 202, `syncContinuing=true` in status) — **not a failure**: the failure counter and back-off are reset, the lease is released, and the next execution is queued (idempotent key `qbo-read-sync:cont:<connection>:<syncId>:<checkpoint seq>:<lease epoch>`; the daily producer is the safety net under a day-scoped variant of that key, so a spent or dead-lettered task can never strand a checkpoint, and each execution also stops at a wall-clock deadline — 45 s soft, measured from the **start of the invocation (token acquisition included)**, plus a hard abort 30 s later of **everything still in flight** (token claim wait, token refresh, the forced refresh after a 401, entity / count / by-id reads, reports), for scheduled and manual executions — in addition to its provider-call budget; see §11 for the end-to-end bound). The earlier fixed 500-page ceiling no longer exists; an arbitrarily large account simply takes more executions.
* **Checkpoint**: `qbo_sync_states.continuation` (JSON, schema-validated; anything unreadable is treated as absent and the sync restarts cleanly) holds the logical `syncId`, mode, the **fixed cutoff**, entity index, keyset cursor, in-progress tie-bucket state and reconciled entities. It is written **in the same transaction as the page it describes**, so a crash can neither lose a persisted page nor record progress for an unpersisted one. Every execution of one logical sync reuses the same `syncId`, mode and cutoff; every mirror row read carries `last_seen_sync_id`.
* **Watermark rule (a permanent skip is excluded only under the documented assumptions R1/R2)**: the durable per-entity watermarks move **only** in `finishSyncRunSuccess`, i.e. after *every* entity is established as exhausted under those assumptions and the reports are stored, and they move to the logical sync's fixed cutoff (never to a later execution's clock). The same transaction clears the checkpoint, so "watermark advanced" and "checkpoint present" can never both be true. A `CONTINUING` or `FAILED` execution leaves the watermarks untouched. **Report-stage failures** (all entities exhausted, a report then fails) never advance them either, and never leave the sync pinned to its old cutoff: a permanent cause (malformed / rejected / forbidden report) or a transient cause that repeats `QBO_SYNC_REPORT_STAGE_MAX_RESUMES` (3) times in a row marks the checkpoint `restart`, so after the back-off the next attempt is a **fresh logical sync** (new `syncId` and cutoff, entities re-read from the unchanged watermark, the re-evaluation marker carried over); fewer transient failures resume the report stage only. The next sync starts at `watermark − 10 min`, which also covers records Intuit indexed late (stamped before the cutoff but visible only after it) and records edited while a sync was paused (stamped after the cutoff). Exercised by `qbo-sync-continuation.db.test.ts` against a fake provider (not Intuit).
* **Keyset pagination** (not offset): each page asks for `LastUpdatedTime >= cursor AND <= cutoff ORDERBY LastUpdatedTime ASC` from position 1. A full page establishes that every second *below* its newest second is complete (the ordering puts them first), so the cursor moves to that newest second; a short page establishes that the remaining window arrived in one response (both rely on the provider honouring ORDERBY and returning every matching row up to MAXRESULTS — validated in the live Sandbox acceptance). Result order is validated (out-of-order ⇒ `PROVIDER_MALFORMED`); a cursor that cannot advance ⇒ `PROVIDER_INCOMPLETE`.
* **Equal-`LastUpdatedTime` buckets larger than a page — identity-inclusion check (not cardinality) — a bounded guarantee, not an atomic snapshot.** Documentation labels (not code identifiers): *completeness mechanism* = keyset bootstrap on `MetaData.LastUpdatedTime` + a two-round identity-inclusion check via documented `count(*)` with `Id IN (…)`; CDC evaluated and not adopted; no atomic snapshot mechanism exists. A count comparison proves only cardinality: a record leaving the second while a late-indexed one enters keeps every count equal. So the bucket is enumerated in passes and is **closed only when the provider reports set inclusion**: for the ids this logical sync stored for that second, `Σ count(second AND Id IN batch) == count(second)` (batches of ≤50 ids), run in **two full rounds**, each followed by a re-read of `count(second)` **and of the number of the entity's records stamped after the cutoff** (an edit moves a record forward and changes that number even when a swap keeps `count(second)` equal; a delete or deactivation does not, so those are caught only through `count(second)` and the batch sums — a delete coinciding with an arrival in the same second is part of residual R1/R2; any change restarts the check). Stored ids that have since left the second match nothing and are harmless; a provider member we lack makes the sum fall short, which restarts the enumeration. Passes that add nothing, or repeated drift, end the run `PROVIDER_INCOMPLETE` (never a silent skip, never a loop). No ordering assumption is used anywhere. Tests: same-count replacement, flip between verification batches, flip while paused at a checkpoint (restart / takeover), provider that counts a record it never serves, reshuffled ties, ignored `STARTPOSITION`.
  * **Official evidence** (Intuit developer documentation; the build container has no DNS, so evidence was retrieved by search from the pages named): *(No snapshot / transaction / read-version mechanism was found in Intuit's documentation for query reads: the query language has no snapshot or isolation clause, results are per call, and the batch endpoint — which can carry query items — is a POST with per-item independent results and no documented read-atomicity, so it is also excluded by the GET-only rule. A single query cannot return an oversized bucket's identity set because a response is capped at 1000 rows.)* *Query operations and syntax* — statements `SELECT * | count(*) FROM <Entity> [WHERE …] [ORDERBY …] [STARTPOSITION] [MAXRESULTS]`; operators `IN, =, <, >, <=, >=, LIKE`; parenthesised lists only for `IN`; **a filter on the `Id` field supports only `=` and `IN`** (no range, so an Id keyset is impossible, which is why inclusion — not Id ordering — is used); max 1000 per response; OR/JOIN/GROUP BY unsupported. *Change data capture operation* — returns entities changed since a timestamp; **covers all API entities except JournalCode, TaxAgency, TimeActivity, TaxCode, TaxRate (so Customer, Invoice and Bill are supported)**; look-back **≤ 30 days**; **max 1000 objects per response** (narrow the window and repeat); deleted objects are returned after active ones carrying `status: Deleted`.
  * **Why CDC is not the completeness mechanism here (decision, not omission).** CDC cannot bootstrap an account (30-day window, 1000-object cap), and the documentation says nothing that a record *becoming visible later with an older `LastUpdatedTime`* appears in a CDC response keyed on a later `changedSince`; so CDC does not by itself close the identified race. It is the right tool for **deletion detection and gap repair**, and remains the planned follow-up slice (record a `Deleted` state, fall back to a full resync when the last sync is older than 30 days). CDC_USED=NO; QUERY_PAGINATION_REMAINS=YES.
  * **Watermark invariant** (documentation label): a durable watermark moves past T only when, for every entity, the read reached a short page of the keyset window or closed every oversized bucket by the identity-inclusion check, after which the next sync still re-reads from `watermark − 10 min`. **Guarantee and residual assumptions.** Each verification read is a separate provider call, so this is not an atomic snapshot. Any single membership change between the start of verification and its last re-read is detected (departure by edit ⇒ post-cutoff count changes; departure by delete/deactivation or an arrival ⇒ total drift or batch-sum shortfall; ⇒ bucket stays open, enumeration restarts, watermark unmoved), exercised by a deterministic sweep (fake provider) that injects the swap after each of the six identity reads. Edits elsewhere in the account also restart the check (fail-closed; each such restart is charged as a stalled pass and the following pass usually adds one more, so a handful of unrelated edits during one bucket's verification can end the run `PROVIDER_INCOMPLETE`, retried later with a fresh logical sync). A coordinated adversary that in the same window deletes/edits a member, makes an unseen record appear, *and* neutralises the post-cutoff count cannot be excluded without provider snapshot semantics — assumption **R1** (the bucket is quiescent while it is checked). Assumption **R2** (distinct): a record that becomes visible *after* our last observation of its second, stamped with that old second, is a provider visibility defect that no polling protocol can observe; the 10-minute overlap covers ordinary indexing delay, and Intuit documents no longer delay.
* **Drift and poisoned checkpoints.** A pass proceeds to the identity-inclusion check only if the provider's count did not change during the pass (`count at end == count at start`); that equality is a precondition, **never** the closure criterion (closure is the identity-inclusion check described above). A record leaving the bucket mid-pass shifts offsets, so the pass restarts instead. Repeated drift/mismatch ⇒ `PROVIDER_INCOMPLETE`, and the checkpoint is flagged `restart`: the next attempt starts a **fresh logical sync** (new `syncId`, new cutoff, stale seen-marks irrelevant) while keeping the durable `changed` flag. Continuation tasks are keyed `<connection>:<syncId>:<checkpoint seq>:<lease epoch>` so neither a retry after a failed execution nor a sequence number reused by a later sync can be swallowed by an already-spent key.
* **Re-evaluation marker.** `changed` is persisted in the checkpoint whenever any execution (including one that later failed) stored a provider change, and is ORed into the final `qbo.sync_completed` event (`reevaluationCandidate`), so a multi-execution or retried sync cannot lose it. Nothing consumes the marker in this slice (adoption into owner snapshots is a later reviewed slice).
* **Missing records (conservative, V26A).** Intuit's query omits inactive (and deleted) objects. A FULL sync (first run and weekly) treats records the logical sync did not see only as *candidates* and re-reads them by id (`GET`, ≤100 per entity per sync, least-recently-attempted first so a standing set cannot starve the rest). A record the provider returns is refreshed (inactive ⇒ `INACTIVE`). A record it cannot positively return (HTTP 404, or HTTP 400 with fault `610`) is counted **`unresolved` and left exactly as stored** — there is no `MISSING` state. Fault 610 is documented by Intuit for *inactive/deleted objects referenced in a request*, not as a statement about reads by id, so it is **not** treated as proof of deletion. Deletion detection (Change Data Capture, `status=Deleted`, 30-day / 1000-object limits) is deliberately deferred to a later reviewed slice. Transient errors (auth, rate limit, outage, timeout) still fail the run.
* **Unseen-record verification terminates.** The by-id candidates of a FULL sync are selected in batches of 100 and a record already verification-attempted in **this logical sync** (attempt stamp at or after the sync's fixed cutoff, whatever the result) is never selected again, so a standing set of unresolvable records cannot keep the sync in `CONTINUING` forever. Every execution verifies at least one candidate before its deadline or call budget may stop it (forward progress); reconciliation of an entity ends when no unattempted candidate is left, and unresolved rows stay exactly as stored.

## 5. Token refresh, failures, back-off

Closed failure vocabulary (`QBO_SYNC_FAILURE_CODES`). `invalid_grant`, a dead refresh token, or a 401 on a token that was *just* refreshed (one forced refresh per token expiry; the allowance re-arms after the new token is accepted) ⇒ connection `REAUTH_REQUIRED` (terminal, never retried, producer stops listing it). Transient provider failures back off 15m→6h; persistent non-auth failures (forbidden, malformed, rejected, company mismatch) 6h→23h; `Retry-After` honoured up to the ceiling. Manual runs ignore back-off (a deliberate human act, rate-limited by the cooldown); scheduled/webhook runs return `NOT_DUE` inside it. One malformed report does not discard the others: the rest are stored, then the run fails `PROVIDER_MALFORMED` (watermarks do not advance).

## 6. Surfaces

| Surface | Path | Gate |
| --- | --- | --- |
| Manual sync | `POST /api/owner/integrations/quickbooks/sync` body `{businessId, connectionId, requestId?}` (strict) | `OWNER_MANAGE`, workspace, human actor |
| Status | `GET /api/owner/integrations/quickbooks/status?businessId=` | `OWNER_VIEW`, workspace |
| Webhook | `POST /api/integrations/quickbooks/webhook` | HMAC signature (no session) |
| Scheduler | task `qbo-read-sync`, producer in `/api/internal/cron/scheduler` | `CRON_SECRET` (existing) |

Tokens, realm, environment, base URL, workspace and actor are never accepted from a caller; the status body contains no realm, token, ciphertext, OAuth state or provider payload. No UI was added (the owner QuickBooks surface is exactly these routes).

**Scheduler cadence**: one task per eligible connection per UTC day, or — when an unfinished sync has a checkpoint — one continuation task per checkpoint position and day (daily key `qbo-read-sync:<connection>:<YYYY-MM-DD>`; continuation key `qbo-read-sync:cont:<connection>:<syncId>:<seq>:<epoch>[:<YYYY-MM-DD>]`, the day suffix only on the producer's safety-net variant). The handler's own follow-up and the producer's day-scoped variant are different keys, so a checkpoint can occasionally have two queued tasks; the second finds the lease free and may run one more real execution (the lease serialises them and each reads the checkpoint fresh, so there is no data effect — only time). Webhook tasks are coalesced to one per connection per lease epoch per 6-hour bucket (`qbo-read-sync:webhook:<connection>:<epoch>:<bucket>`), so a spent BUSY/NOT_DUE task cannot swallow later hints beyond that window, matching the platform's single daily cron (`0 3 * * *`). Rationale: QuickBooks reports change daily and the platform cron is daily. Webhook-triggered tasks (when the webhook is later enabled) are executed by the same scheduler drain, i.e. at the next scheduler invocation — with the current single daily cron that is *not* intraday; intraday freshness would need an additional drain trigger, which is out of scope. Producer scans are bounded (10 pages of 200), skip non-ACTIVE/leased/backing-off connections and other environments, and registration is idempotent. A connection that already has a **pending or running** `qbo-read-sync` task (from any day, or a continuation) is **not queued again**, so an undrained backlog cannot grow by one task per connection per day; the scan result reports `skippedOpenTask`, the open `openTasks` backlog and `truncated` (the page cap was reached with more connections possibly remaining), and the cron response carries it.

## 7. Owner-data safety / provenance rules (`qbo-provenance-policy.ts`) — *groundwork: not wired to any caller in this slice*

1. Manual values are never overwritten; a material difference is a *conflict* with the QuickBooks figure offered as a suggestion.
2. QuickBooks fills gaps only, tagged with observation + connection + fetch time + stored revision + content hash, only when the observation's report and metric are the ones the field maps to (`QBO_FIELD_SOURCES`), and capped at confidence 0.85.
3. Currency must equal the business currency — no conversion, no adoption otherwise (the seeded business default is INR; QuickBooks sandbox is USD).
4. Period/as-of must match the target snapshot (flow metrics: exactly the period; balance-sheet metrics: at period end; aged metrics: within 7 days), Accrual basis only, staleness measured on the as-of date.
5. Internally inconsistent reports (gross profit, aging sums, negative overdue from credits, unbalanced balance sheet), absent metrics (never zero) and archived businesses are never adopted.
Because this slice performs **no** adoption, the mandatory adaptive re-evaluation is *prepared*, not executed: a successful sync that changed data emits `qbo.sync_completed` with `reevaluationCandidate: true`; routing that into BusinessConditionProfile / InterventionMode / phase / priority / cadence / health belongs to the adoption slice.

## 8. Webhook — contract (derived from Intuit documentation)

Derived from Intuit's developer documentation as retrieved by search — the pages themselves could not be fetched from the build container (webhooks overview, CloudEvents migration guide, and *Validate the webhook notification*):

* **Format**: CloudEvents 1.0, delivered as a JSON **array** of events: `specversion`, `id`, `source`, `type` (`qbo.<entity>.<operation>.v1`), `datacontenttype`, `time`, `intuitentityid`, `intuitaccountid` (= the QuickBooks company/realm id), `data`. The legacy `eventNotifications` envelope is still parsed.
* **Signature**: header **`intuit-signature`** = **Base64** of HMAC-SHA256 over the **exact raw request bytes**, keyed by the app's **webhook verifier token**. Verification is constant-time over the raw bytes before any parsing; a body re-serialised in any way no longer verifies. Covered by a known-answer fixture vector computed independently with `openssl` and by the contract tests (not exercised against a live Intuit delivery) in `qbo-webhook-contract.test.ts` (exact bytes, Base64-not-hex, wrong algorithm, wrong/absent token, tamper).
* **Environments are configured separately**: Sandbox and Production webhooks each have their own endpoint URL and verifier token in the Intuit developer portal. The receiver resolves the verifier token and realm per environment (`QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN` for the configured environment) and drops an event whose realm does not belong to that environment's connection.
* **Delivery**: at-least-once and unordered; acknowledge with HTTP 200 quickly. The receiver verifies, records a payload-free dedupe ledger row (a failed hand-off is `RETRY_PENDING` and re-delivered by Intuit), sets a **hint** on the connection and never trusts event content — the actual data always comes from the read sync.
* **Not configured**: no webhook is registered in Intuit by this slice (`WEBHOOK_INTUIT_CONFIGURED=NO`); without `QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN` the endpoint answers 503. Registration, the endpoint-validation handshake in the portal, and a live delivery remain a later, explicitly authorized acceptance step.

## 9. Known limitations

* No UI; no adoption of QuickBooks values into owner snapshots; no business-condition re-evaluation yet (§7).
* The per-realm rate limiter is process-local (existing limitation); the single sync lease serializes the realm in practice.
* The live behaviour of `MetaData.LastUpdatedTime` filtering/ordering in Intuit's query language, of `SELECT count(*)` with that filter, and the exact row/group names of the four report payloads (ProfitAndLoss, BalanceSheet, AgedReceivables, AgedPayables) are implemented to Intuit's documented shapes and unit-tested against fixtures, but are **not proven against the live Sandbox**. Report-shape validation is **deliberately left to the live Sandbox acceptance** (§10); until then report observations are not adopted into any owner figure (§7).
* Aged reports accumulate one observation per day per connection (no deletion by design); report observations keep one step of history only.
* `report_date` is the UTC date, not the company's local date. Balance-sheet AR/AP is not yet reconciled against the aged totals or open invoice balances (only the balance equation, gross profit and aging sums are checked).
* All mirror tables are internal-only: no route returns records or observations (only counts). Customer display names and document numbers are retained (e-mail, phone, address and notes are not).
* Realm exclusivity across tenants is enforced by the existing partial unique index `qbo_connections_live_realm_key`.
* A platform-killed sync leaves a `RUNNING` run that the next lease acquisition marks `ABANDONED` (no data is lost: pages are persisted as they go and replays are idempotent).
* A back-off never exceeds 23 h so a retry cannot slip a whole extra day behind the daily cron.
* A FULL sync reads every Customer/Invoice/Bill over as many bounded executions as needed (§4); there is no cap on total dataset size. **One exception, fail-closed:** the identity-inclusion check of a single equal-timestamp bucket is designed to complete within one uninterrupted verification (two rounds of ≈N/50 calls plus passes); with the default 100-call / 45 s execution budget that is roughly 2,000 records sharing one second. A larger bucket, or any account-wide edit between executions of the same verification, restarts the check; three stalled restarts end the run `PROVIDER_INCOMPLETE` (retried later, watermark unmoved). Such accounts need a raised execution budget or provider snapshot semantics. Intuit's rate limits govern wall-clock time, not correctness.
* Deletions at Intuit are not detected in this slice (no `MISSING` state); a deleted record stays as last stored and counts toward `unresolved` when a FULL sync fails to re-read it. Change Data Capture is the planned mechanism.

## 11. Audit-driven additions (V26A final)

* **Re-evaluation marker** (`changed`) is written into the checkpoint inside the same transaction as every page/record write that inserted or updated data, and by every report observation that changed; a fresh logical sync writes its empty checkpoint **in the same transaction as its first record** (CompanyInfo), never earlier. A crash, timeout, takeover or failed attempt therefore cannot lose it.
* **Oversized buckets with rejected records** (a deterministic fail-closed terminal condition, visible as `PROVIDER_INCOMPLETE` on every attempt, until the provider data changes): records the normalizer rejects (e.g. an invoice without `TotalAmt`) are listed by id (≤50, queryable ids only) in the bucket state and confirmed with `Id IN`; more than 50, or an unqueryable id, ends the run `PROVIDER_INCOMPLETE` (fail closed).
* **Aged reports**: a body with customer rows but no grand-total section is malformed; only an empty `Rows` is a zero. Aged reports still do not assert an `EndPeriod` echo (live Sandbox acceptance item).
* **Token refresh**: a transient refresh failure after a 401 is a retryable failure with back-off; only a dead grant marks the connection `REAUTH_REQUIRED`.
* **Connect callback**: the client-relayed `realmId` is bound only after one read-only `companyinfo` GET with the newly issued token confirms that company and id.
* **Response bodies** from Intuit are read as a stream with a running byte cap; the webhook body likewise (413 above 1 MiB).
* **Bounded drain and end-to-end deadline**: the cron drain claims 2 tasks per pass (`processDue(handlers, { maxClaim })`, default 50 elsewhere), keeps claiming while rows were claimed (a pass whose tasks all failed does not end it), starts a pass only inside an 80 s budget and declares `maxDuration = 300`. **One QuickBooks execution is bounded by `QBO_EXECUTION_WORST_CASE_MS` = 45 s soft deadline + 30 s hard-abort grace + 10 s finalisation allowance = 85 s, measured from the start of the invocation (token acquisition included)**: the soft deadline stops new work at a durable checkpoint; at the grace every request still in flight is aborted (the run fails `CANCELLED` and resumes from its checkpoint); the finalisation allowance is the budget assumed for the few single-statement transactions that follow (it is not a timer). The route additionally passes an absolute invocation deadline (`INVOCATION_DEADLINE_MS` = 285 s from the start) to every task, and an execution pulls its soft deadline in so that soft + grace + allowance still ends before it. So 80 s + 2 × 85 s = 250 s ≤ 285 s < 300 s. Not covered: other task types' handlers (unbounded, as before) and a platform kill; a kill can strand at most 2 `running` rows (reclaimed by lease expiry) and a sync lease of up to 15 minutes, with no data loss. **Fairness**: QuickBooks tasks are claimed *after* every other due task (oldest first within each class), so a QuickBooks backlog cannot starve the email-retry, reassessment, risk-review and finance scans; QuickBooks tasks use whatever drain budget remains. A single QuickBooks execution may therefore be followed by another within the same drain (the follow-up is due immediately). The webhook hint timestamp is monotonic (an older delivery cannot move it back).
* **Report-stage restart and OAuth safety (V26A repair)**: see §4 (report-stage failures never pin a sync to an old cutoff). The connect callback revokes a just-issued grant at Intuit **only when it is certain the grant is not stored AND no not-disconnected connection holds the verified company** (an Intuit revocation may be app/company-wide); the token-encryption key is checked **before** the authorization code is exchanged. A grant is deliberately **not** revoked, and remains live at Intuit until an operator revokes it there (Intuit developer portal / `revokeQboToken`), when: another connection holds the company (`REALM_ALREADY_BOUND`); the one-time state was lost to a race (`AUTHORIZATION_NOT_CONSUMED` / `_ALREADY_FINALIZED`); the commit outcome is unknown (a non-domain error from the finalize transaction); the holder lookup itself fails; or a revocation request fails. A refresh whose `invalid_grant` answer concerns a token that was already superseded by a newer stored revision (a refresh claim that lapsed while another refresher rotated) never marks the connection `REAUTH_REQUIRED`; the `REAUTH_REQUIRED` mark itself is fenced on the revision that was presented.
* **Exchange rates** are kept with up to 8 fractional digits (amounts keep 4); a non-zero rate too small to represent is stored as absent, never as `0`.
* **Known, accepted P2 items** (not fixed in this slice; none changes what V26A stores or sends): the provenance policy (not wired yet) compares adopted values as doubles and has no tenant/connection-status binding — to be closed in the adoption slice; report consistency checks are skipped when their anchor groups are absent (live-Sandbox shape validation must confirm the groups before any adoption); re-evaluation remains a marker only — `reevaluationCandidate` has no consumer yet (section 7); the webhook ledger has **no retention job** (one row per delivered event: a governed-record deletion policy must be decided **before** the webhook is registered with Intuit) and the webhook performs sequential database work per event and buffers up to 1 MiB before the configuration check; task construction is duplicated in three small places; the status flag `syncContinuing` can stay true next to a terminal `REAUTH_REQUIRED` (cosmetic; reconnect resumes safely); a provider redirect on a credentialed request is retried as a transient failure; continuation follow-ups run in the same drain when the 80 s budget allows, otherwise at the next daily drain, and a failed continuation execution is retried by the next daily producer, not at its back-off time (a very large account may need several days; this is bounded by the single daily cron, not by correctness); the shared drain now claims 2 tasks per pass (at most 200 passes) instead of 25 passes of 50, so its per-invocation ceiling is lower; aged observations are one row per UTC day (no retention job); the report stage ignores the soft deadline and is bounded only by the hard abort; lease/cutoff arithmetic uses the application clock; observation history keeps one prior revision; a backoff of up to 23 h can span a cron boundary; infrastructure aborts are charged as transient failures; the `CONTINUING` task result is recorded as success on the automation page (the audit event shows it is unfinished).
