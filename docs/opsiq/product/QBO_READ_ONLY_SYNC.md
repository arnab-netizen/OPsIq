# QuickBooks Online — READ-ONLY synchronization (V26 / V26A hardening)

`QBO_READ_ONLY` · `NO_QBO_WRITE_API` · `PRODUCTION_MIGRATION_REQUIRED=YES` (`20261010090000_qbo_read_only_sync_persistence`, additive) · `NO_EVIDENCE_ADOPTION` · `WEBHOOK_INTUIT_CONFIGURED=NO` · `LIVE_QBO_CALL_EXECUTED=NO`

Builds on the proven OAuth + persistence foundation (`QBO_CONNECTION_PERSISTENCE.md`). Adds the first read-only sync, a manual owner trigger, a token-free status API, a scheduled sync, and a signature-verified webhook that is only an event *hint*.

## 1. Source audit — answers to the Phase 1 questions

| Question | Answer (source of truth) |
| --- | --- |
| How is an ACTIVE connection resolved business-safely? | `resolveSyncableConnection({workspaceId, businessId, connectionId})` in `qbo-sync-store.service.ts` selects by the full triple; a connection of another workspace/business is indistinguishable from a missing one. Status must be `ACTIVE`, business active and non-fixture, and `connection.environment` must equal the configured environment. The scheduler/webhook entry recovers the business from the connection row by (claimed workspace, connection id) only. |
| How are encrypted tokens loaded? | `loadQboTokensForUse` (`qbo-connection.service.ts`) — server-side only, `decryptOAuthToken` with the workspace-bound key. `getUsableQboAccessToken` is the only caller on the sync path; the plaintext never leaves the process (not in outcomes, audit payloads, logs or errors). |
| How does refresh happen? | `getUsableQboAccessToken` refreshes only when the access token has < 2 minutes left (or once per sync after an API 401) via `refreshQboTokens`; never retried inside the service (a lost response may already have rotated the token). |
| How do CAS/revision prevent stale refresh writers? | Refreshers of one connection are first serialized by a short DB claim (`qbo_sync_states.refresh_claim_*`, no open transaction), so Intuit — which ROTATES the refresh token — is called once; a waiter re-reads the stored tokens instead of refreshing again. The grant is then persisted with `rotateQboTokens({expectedRevision})` — a conditional UPDATE on `revision` (retried on transient DB errors with the same grant); `STALE_REVISION` ⇒ the loser discards its grant and adopts the stored one. A forced refresh (after an API 401) names the revision that was rejected and is a no-op if a newer revision is stored. |
| How do scheduled jobs obtain workspace/business? | `ScheduledTask.workspaceId` is set at enqueue and handed to the handler as `context.workspaceId` (never from payload). The payload carries only `connectionId`; the business comes from the connection row. |
| How is external-source data stored with provenance? | The generic `External*` tables are not tenant-/realm-aware (same reason as `QBO_SPECIFIC` in the persistence doc), so sync data lives in QBO-specific mirror tables keyed by connection, with run ids, provider timestamps/SyncToken, content hashes and fetch times. |
| Which owner-facing records can safely receive QBO data? | **None in this slice.** `OwnerFinancialSnapshot`/`OwnerCashflowSnapshot` are owner-attested; QuickBooks values are held as provider observations and adopted only through `resolveFinancialFieldPrecedence` (§7) in a later reviewed slice. |

## 2. Supported sources (derived, not assumed)

`SUPPORTED_QBO_READ_ENTITIES = CompanyInfo, Customer, Invoice, Bill, ProfitAndLoss(report), BalanceSheet(report), AgedReceivables(report), AgedPayables(report)`

Derived from the fields OpsIQ's finance/cashflow snapshots consume (table in `qbo-sync-model.ts`): revenue/COGS ← ProfitAndLoss; cash ← BalanceSheet `BankAccounts`; receivables/payables ← BalanceSheet + aged reports (cross-checked); overdue ← aged reports (every non-"Current" bucket); customer/order counts ← Customer, Invoice; payables detail ← Bill. Deliberately **not** synced: Vendor, Account, Payment, Purchase, CashFlow, TrialBalance, payroll and everything else in the read catalog. Adding a source is a reviewed change to `qbo-sync-model.ts` **and** to `qbo-foundation-boundaries.test.ts`.

Every provider request goes through `createQboReadClient` (GET-only). The sync service calls exactly `companyInfo`, `paginate`, `report`.

## 3. Persistence (additive migration)

| Table | Purpose |
| --- | --- |
| `qbo_sync_states` | One row per connection: **the lease** (`lease_token`, `lease_run_id`, `lease_expires_at`, fencing `lease_epoch`), the token-refresh claim, last attempt/success/full-sync, outcome, sanitized `last_error_code`, `consecutive_failures`, `next_attempt_not_before`, per-entity `watermarks`, the durable **`continuation`** checkpoint of an unfinished sync, `last_change_at`, `webhook_hint_at`. |
| `qbo_sync_runs` | One attempt; `UNIQUE(connection_id, idempotency_key)` ⇒ replay. Status `RUNNING/SUCCEEDED/FAILED/ABANDONED`, counts, sanitized error code. |
| `qbo_synced_records` | Normalized, PII-minimal copy of Customer/Invoice/Bill/CompanyInfo: provider id, SyncToken, provider `LastUpdatedTime`, record state `ACTIVE/INACTIVE`, content hash, revision, first/last-seen run and last-seen *logical sync*, last by-id verification attempt, fetch time. `UNIQUE(connection, entity, provider id)`. |
| `qbo_report_observations` | Parsed report per (report, period, basis): currency, metrics as decimal strings (absent ≠ 0), inconsistency flags, hash, revision and ONE step of history (`previous_metrics`). |
| `qbo_webhook_events` | Dedup ledger of verified hints (no payload). Tenant columns are NULL for an unknown realm. |

Every sync table references `qbo_connections(id, workspace_id, business_id)` by composite FK (new unique index `qbo_connections_tenant_business_key`), so a row cannot name another tenant's connection. No token column exists outside `qbo_connection_tokens` (machine-checked). Nothing is deleted, and no record is ever flagged as deleted by this slice (§4, *Missing records*).

## 4. Lease, idempotency, resumption

* **One lease per connection**: acquisition is one conditional `UPDATE … WHERE lease_token IS NULL OR lease_expires_at <= now` inside the same transaction that records the `RUNNING` run; the loser gets a typed `BUSY` (HTTP 409) and nothing runs. TTL 15 minutes (above the worst-case retry budget of one provider request) and extended **before every provider call** and by every persisted page.
* **Stale workers cannot write**: every persisted page/report re-verifies *and extends* the lease in its own transaction; finishing releases it with a CAS. The fence is the **(token, epoch)** pair — a takeover replaces the token, so a taken-over worker always fails with `QboLeaseLostError`; an expired-but-untaken lease can still be finished by its owner (work is not discarded when nobody competed). The abandoned run is marked `ABANDONED` and audited.
* **Idempotency keys** carry the lease epoch: MANUAL `manual:<requestId>`; SCHEDULED `scheduled:<UTC day>:<epoch>`; WEBHOOK `webhook:<15-min>:<epoch>`. Two triggers racing from the same state collide on the unique key and replay; a retry after a failed / abandoned / crashed attempt (epoch moved on) runs under a fresh key, so a failure never "swallows" the day. Same-day repeat of a *successful* scheduled sync is `NOT_DUE`; a webhook-triggered run happens only while an unserved hint exists. A non-successful replay is never reported as success (HTTP 409).
* **MANUAL cooldown**: 60 s per connection (each run costs ~11 provider calls).
* **Bounded work per execution, durable checkpoint, no dataset-size cap.** One execution spends at most `QBO_SYNC_PAGES_PER_EXECUTION` (100) provider query calls (pages and `count(*)` probes). When the budget is spent before exhaustion is *proven*, the run ends `PARTIAL` (outcome `CONTINUING`, HTTP 202, `syncContinuing=true` in status) — **not a failure**: the failure counter and back-off are reset, the lease is released, and the next execution is queued (idempotent key `qbo-read-sync:cont:<connection>:<checkpoint seq>`; the daily producer is the safety net for a lost task). The earlier fixed 500-page ceiling no longer exists; an arbitrarily large account simply takes more executions.
* **Checkpoint**: `qbo_sync_states.continuation` (JSON, schema-validated; anything unreadable is treated as absent and the sync restarts cleanly) holds the logical `syncId`, mode, the **fixed cutoff**, entity index, keyset cursor, in-progress tie-bucket state and reconciled entities. It is written **in the same transaction as the page it describes**, so a crash can neither lose a persisted page nor record progress for an unpersisted one. Every execution of one logical sync reuses the same `syncId`, mode and cutoff; every mirror row read carries `last_seen_sync_id`.
* **Watermark rule (no permanent skip)**: the durable per-entity watermarks move **only** in `finishSyncRunSuccess`, i.e. after *every* entity is proven exhausted and the reports are stored, and they move to the logical sync's fixed cutoff (never to a later execution's clock). The same transaction clears the checkpoint, so "watermark advanced" and "checkpoint present" can never both be true. A `CONTINUING` or `FAILED` execution leaves the watermarks untouched. The next sync starts at `watermark − 10 min`, which also covers records Intuit indexed late (stamped before the cutoff but visible only after it) and records edited while a sync was paused (stamped after the cutoff). Proven by `qbo-sync-continuation.db.test.ts`.
* **Keyset pagination** (not offset): each page asks for `LastUpdatedTime >= cursor AND <= cutoff ORDERBY LastUpdatedTime ASC` from position 1. A full page proves every second *below* its newest second is complete (the ordering puts them first), so the cursor moves to that newest second; a short page proves the remaining window arrived in one response. Result order is validated (out-of-order ⇒ `PROVIDER_MALFORMED`); a cursor that cannot advance ⇒ `PROVIDER_INCOMPLETE`.
* **Equal-`LastUpdatedTime` buckets larger than a page — set-inclusion proof (not cardinality).** `INTUIT_COMPLETENESS_MECHANISM = keyset bootstrap on MetaData.LastUpdatedTime + identity-inclusion proof via documented count(*) with Id IN (…), two rounds; CDC evaluated and not adopted`. A count comparison proves only cardinality: a record leaving the second while a late-indexed one enters keeps every count equal. So the bucket is enumerated in passes and is **closed only when the provider itself confirms set inclusion**: for the ids this logical sync stored for that second, `Σ count(second AND Id IN batch) == count(second)` (batches of ≤50 ids), run in **two full rounds**, each followed by a re-read of `count(second)`. Stored ids that have since left the second match nothing and are harmless; a provider member we lack makes the sum fall short, which restarts the enumeration. Passes that add nothing, or repeated drift, end the run `PROVIDER_INCOMPLETE` (never a silent skip, never a loop). No ordering assumption is used anywhere. Tests: same-count replacement, flip between verification batches, flip while paused at a checkpoint (restart / takeover), provider that counts a record it never serves, reshuffled ties, ignored `STARTPOSITION`.
  * **Official evidence** (Intuit developer documentation; the build container has no DNS, so evidence was retrieved by search from the pages named): *Query operations and syntax* — statements `SELECT * | count(*) FROM <Entity> [WHERE …] [ORDERBY …] [STARTPOSITION] [MAXRESULTS]`; operators `IN, =, <, >, <=, >=, LIKE`; parenthesised lists only for `IN`; **a filter on the `Id` field supports only `=` and `IN`** (no range, so an Id keyset is impossible, which is why inclusion — not Id ordering — is used); max 1000 per response; OR/JOIN/GROUP BY unsupported. *Change data capture operation* — returns entities changed since a timestamp; **covers all API entities except JournalCode, TaxAgency, TimeActivity, TaxCode, TaxRate (so Customer, Invoice and Bill are supported)**; look-back **≤ 30 days**; **max 1000 objects per response** (narrow the window and repeat); deleted objects are returned after active ones carrying `status: Deleted`.
  * **Why CDC is not the completeness mechanism here (decision, not omission).** CDC cannot bootstrap an account (30-day window, 1000-object cap), and the documentation says nothing that a record *becoming visible later with an older `LastUpdatedTime`* appears in a CDC response keyed on a later `changedSince`; so CDC does not by itself close the identified race. It is the right tool for **deletion detection and gap repair**, and remains the planned follow-up slice (record a `Deleted` state, fall back to a full resync when the last sync is older than 30 days). `CDC_USED=NO`; `QUERY_PAGINATION_REMAINS=YES`.
  * **Invariant** (`WATERMARK_INVARIANT`): a durable watermark moves past T only when, for every entity, the read reached a short page of the keyset window or closed every oversized bucket by the inclusion proof, after which the next sync still re-reads from `watermark − 10 min`. **Irreducible assumption:** a record that becomes visible *after* our last observation of its second, stamped with that old second, is a provider visibility defect that no polling protocol can observe; the 10-minute overlap covers ordinary indexing delay, and Intuit documents no longer delay.
* **Drift and poisoned checkpoints.** A pass closes a bucket only if the provider's count did not change during the pass (`count at end == count at start`) *and* equals the stored distinct records; a record leaving the bucket mid-pass shifts offsets, so the pass restarts instead. Repeated drift/mismatch ⇒ `PROVIDER_INCOMPLETE`, and the checkpoint is flagged `restart`: the next attempt starts a **fresh logical sync** (new `syncId`, new cutoff, stale seen-marks irrelevant) while keeping the durable `changed` flag. Continuation tasks are keyed `<connection>:<syncId>:<checkpoint seq>:<lease epoch>` so neither a retry after a failed execution nor a sequence number reused by a later sync can be swallowed by an already-spent key.
* **Re-evaluation marker.** `changed` is persisted in the checkpoint whenever any execution (including one that later failed) stored a provider change, and is ORed into the final `qbo.sync_completed` event (`reevaluationCandidate`), so a multi-execution or retried sync cannot lose it. Nothing consumes the marker in this slice (adoption into owner snapshots is a later reviewed slice).
* **Missing records (conservative, V26A).** Intuit's query omits inactive (and deleted) objects. A FULL sync (first run and weekly) treats records the logical sync did not see only as *candidates* and re-reads them by id (`GET`, ≤100 per entity per sync, least-recently-attempted first so a standing set cannot starve the rest). A record the provider returns is refreshed (inactive ⇒ `INACTIVE`). A record it cannot positively return (HTTP 404, or HTTP 400 with fault `610`) is counted **`unresolved` and left exactly as stored** — there is no `MISSING` state. Fault 610 is documented by Intuit for *inactive/deleted objects referenced in a request*, not as a statement about reads by id, so it is **not** treated as proof of deletion. Deletion detection (Change Data Capture, `status=Deleted`, 30-day / 1000-object limits) is deliberately deferred to a later reviewed slice. Transient errors (auth, rate limit, outage, timeout) still fail the run.

## 5. Token refresh, failures, back-off

Closed failure vocabulary (`QBO_SYNC_FAILURE_CODES`). `invalid_grant`, a dead refresh token, or a 401 on a token that was *just* refreshed (one forced refresh per token expiry; the allowance re-arms after the new token is accepted) ⇒ connection `REAUTH_REQUIRED` (terminal, never retried, producer stops listing it). Transient provider failures back off 15m→6h; persistent non-auth failures (forbidden, malformed, rejected, company mismatch) 6h→24h; `Retry-After` honoured up to the ceiling. Manual runs ignore back-off (a deliberate human act, rate-limited by the cooldown); scheduled/webhook runs return `NOT_DUE` inside it. One malformed report does not discard the others: the rest are stored, then the run fails `PROVIDER_MALFORMED` (watermarks do not advance).

## 6. Surfaces

| Surface | Path | Gate |
| --- | --- | --- |
| Manual sync | `POST /api/owner/integrations/quickbooks/sync` body `{businessId, connectionId, requestId?}` (strict) | `OWNER_MANAGE`, workspace, human actor |
| Status | `GET /api/owner/integrations/quickbooks/status?businessId=` | `OWNER_VIEW`, workspace |
| Webhook | `POST /api/integrations/quickbooks/webhook` | HMAC signature (no session) |
| Scheduler | task `qbo-read-sync`, producer in `/api/internal/cron/scheduler` | `CRON_SECRET` (existing) |

Tokens, realm, environment, base URL, workspace and actor are never accepted from a caller; the status body contains no realm, token, ciphertext, OAuth state or provider payload. No UI was added (`OWNER_QBO_SURFACE` is exactly these routes).

**Scheduler cadence**: one task per eligible connection per UTC day (`qbo-read-sync:<connection>:<YYYY-MM-DD>`), matching the platform's single daily cron (`0 3 * * *`). Rationale: QuickBooks reports change daily and the platform cron is daily. Webhook-triggered tasks (when the webhook is later enabled) are executed by the same scheduler drain, i.e. at the next scheduler invocation — with the current single daily cron that is *not* intraday; intraday freshness would need an additional drain trigger, which is out of scope. Producer scans are bounded (200), skip non-ACTIVE/leased/backing-off connections and other environments, and registration is idempotent.

## 7. Owner-data safety / provenance rules (`qbo-provenance-policy.ts`)

1. Manual values are never overwritten; a material difference is a *conflict* with the QuickBooks figure offered as a suggestion.
2. QuickBooks fills gaps only, tagged with observation + connection + fetch time and capped at confidence 0.85.
3. Currency must equal the business currency — no conversion, no adoption otherwise (the seeded business default is INR; QuickBooks sandbox is USD).
4. Period/as-of must match the target snapshot (flow metrics: exactly the period; balance-sheet metrics: at period end; aged metrics: within 7 days), Accrual basis only, staleness measured on the as-of date.
5. Internally inconsistent reports (gross profit, aging sums, negative overdue from credits, unbalanced balance sheet), absent metrics (never zero) and archived businesses are never adopted.
Because this slice performs **no** adoption, the mandatory adaptive re-evaluation is *prepared*, not executed: a successful sync that changed data emits `qbo.sync_completed` with `reevaluationCandidate: true`; routing that into BusinessConditionProfile / InterventionMode / phase / priority / cadence / health belongs to the adoption slice.

## 8. Webhook — verified contract

Verified against Intuit's current developer documentation (webhooks overview, CloudEvents migration guide, and *Validate the webhook notification*):

* **Format**: CloudEvents 1.0, delivered as a JSON **array** of events: `specversion`, `id`, `source`, `type` (`qbo.<entity>.<operation>.v1`), `datacontenttype`, `time`, `intuitentityid`, `intuitaccountid` (= the QuickBooks company/realm id), `data`. The legacy `eventNotifications` envelope is still parsed.
* **Signature**: header **`intuit-signature`** = **Base64** of HMAC-SHA256 over the **exact raw request bytes**, keyed by the app's **webhook verifier token**. Verification is constant-time over the raw bytes before any parsing; a body re-serialised in any way no longer verifies. Proven by a known-answer vector computed independently with `openssl` and by the contract tests in `qbo-webhook-contract.test.ts` (exact bytes, Base64-not-hex, wrong algorithm, wrong/absent token, tamper).
* **Environments are configured separately**: Sandbox and Production webhooks each have their own endpoint URL and verifier token in the Intuit developer portal. The receiver resolves the verifier token and realm per environment (`QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN` for the configured environment) and drops an event whose realm does not belong to that environment's connection.
* **Delivery**: at-least-once and unordered; acknowledge with HTTP 200 quickly. The receiver verifies, records a payload-free dedupe ledger row (a failed hand-off is `RETRY_PENDING` and re-delivered by Intuit), sets a **hint** on the connection and never trusts event content — the actual data always comes from the read sync.
* **Not configured**: no webhook is registered in Intuit by this slice (`WEBHOOK_INTUIT_CONFIGURED=NO`); without `QUICKBOOKS_WEBHOOK_VERIFIER_TOKEN` the endpoint answers 503. Registration, the endpoint-validation handshake in the portal, and a live delivery remain a later, explicitly authorized acceptance step.

## 9. Known limitations

* No UI; no adoption of QuickBooks values into owner snapshots; no business-condition re-evaluation yet (§7).
* The per-realm rate limiter is process-local (existing limitation); the single sync lease serializes the realm in practice.
* The live behaviour of `MetaData.LastUpdatedTime` filtering/ordering in Intuit's query language, of `SELECT count(*)` with that filter, and the exact row/group names of the four report payloads (ProfitAndLoss, BalanceSheet, AgedReceivables, AgedPayables) are implemented to Intuit's documented shapes and unit-tested against fixtures, but are **not proven against the live Sandbox**. Report-shape validation is **deliberately left to the live Sandbox acceptance** (§10); until then report observations are not adopted into any owner figure (§7).
* Aged reports accumulate one observation per day per connection (no deletion by design); report observations keep one step of history only.
* `report_date` is the UTC date, not the company's local date. Balance-sheet AR/AP is not yet reconciled against the aged totals or open invoice balances (only the balance equation, gross profit and aging sums are checked).
* All mirror tables are internal-only: no route returns records or observations (only counts). Customer display names and document numbers are retained (e-mail, phone, address and notes are not).
* Realm exclusivity across tenants is enforced by the existing partial unique index `qbo_connections_live_realm_key`.
* The scheduler cron route declares no `maxDuration`; a platform-killed sync leaves a `RUNNING` run that the next lease acquisition marks `ABANDONED` (no data is lost: pages are persisted as they go and replays are idempotent).
* A back-off never exceeds 23 h so a retry cannot slip a whole extra day behind the daily cron.
* A FULL sync reads every Customer/Invoice/Bill over as many bounded executions as needed (§4); there is no dataset-size cap. Intuit's rate limits govern wall-clock time, not correctness.
* Deletions at Intuit are not detected in this slice (no `MISSING` state); a deleted record stays as last stored and counts toward `unresolved` when a FULL sync fails to re-read it. Change Data Capture is the planned mechanism.
