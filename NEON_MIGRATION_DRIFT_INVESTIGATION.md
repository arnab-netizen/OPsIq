## 3. Ghost Migration Analysis

| Field | Value |
|---|---|
| Ghost name | `1778679447_add_aggregate_locks` |
| Prefix type | Unix timestamp (epoch seconds) |
| Unix timestamp decoded | `2026-05-13 13:37:27 UTC` |
| Local migration with same suffix | `20260511_add_aggregate_locks` (May 11, 2026 — 2 days earlier) |
| Ghost in git history | **NEVER** — no commit, no deleted file, no reference |
| Ghost in local `prisma/migrations/` | **ABSENT** |
| Prisma classification | "migration from the database not found locally" |

**Timestamp naming pattern:**
Standard Prisma `migrate dev` uses date-based prefixes (`YYYYMMDD_HHMMSS`).
Unix epoch prefixes (`1778679447_`) are generated by:
- `prisma migrate diff --script` piped into a manually named file, OR
- Direct SQL execution followed by manual `INSERT INTO _prisma_migrations`, OR
- A tool or script that called the Prisma internals with a different naming convention.

The most likely scenario: someone ran `prisma db push` or `prisma migrate dev` directly against the Neon database from a local machine on **May 13, 2026**, 2 days after `20260511_add_aggregate_locks` was committed. That session created a migration record with a Unix timestamp name in `_prisma_migrations`, but the generated folder was either never committed or was immediately renamed/deleted.

## 5. Root Cause Classification

**Primary: B — Neon DB was previously used by another branch/app**

On or around **May 13, 2026**, a separate CLI session ran migration tooling directly against the Neon database (likely `prisma migrate dev` or a manual `prisma migrate diff` workflow from a development machine). This created a `_prisma_migrations` record with a Unix timestamp name (`1778679447_add_aggregate_locks`) for work that was already captured in the committed migration `20260511_add_aggregate_locks`. The folder was never pushed to the repo.

**Secondary: A — Migration folder deleted from repo (or never committed)**

The session that created `1778679447_add_aggregate_locks` either:
- Generated a migration folder that was immediately discarded, OR
- Only inserted a row into `_prisma_migrations` without creating a local folder.

**Excluded causes:**
- D (rename): The local `20260511_add_aggregate_locks` still exists — no rename occurred.
- E (wrong database): Neon host confirmed as the correct test endpoint.
- F (squash): No evidence of migration squashing in git history.

## 6. Impact Assessment

**Does this block `prisma migrate deploy`?**

`prisma migrate deploy` (the production-safe deploy command) does NOT fail on ghost migrations. It:
1. Ignores entries in `_prisma_migrations` that have no corresponding local folder.
2. Applies the 22 pending local migrations in order.
3. Succeeds if no SQL conflicts exist.

**Is there a SQL conflict risk?**

The ghost `1778679447_add_aggregate_locks` ran SQL that created `aggregate_locks` table and `idx_aggregate_locks_workspace` index. These are the same objects that `20260511_add_aggregate_locks` also creates. Because `20260511_add_aggregate_locks` uses `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, **there is no conflict**. Both migrations are idempotent for the objects they create.

The 22 pending migrations operate on different tables (startup_status, approval_workflow, recovery_mode, finance modules, etc.). No conflict with the ghost is expected.

**Conclusion:** `prisma migrate deploy` against the current Neon DB should succeed. The ghost migration is a cosmetic entry in `_prisma_migrations` and does not block deployment.

## 8. Final Recommendation

**Recommended:** `CREATE_FRESH_NEON_TEST_DB`

**Rationale:** The Neon test DB accumulated an out-of-band migration entry that is not in git. While `migrate deploy` would likely succeed against the current DB (the ghost uses `IF NOT EXISTS`), the cleanest approach for a test database is to start from a known-good baseline. A fresh Neon branch (Neon supports instant branching from the console) gives:

1. Zero drift — no ghost migration entries.
2. Clean `migrate deploy` history — all 59 local migrations applied in order.
3. No uncertainty about what SQL the ghost actually executed.
4. A reproducible state that matches what LANE_B already verified.

**Fallback:** If provisioning a new Neon branch is undesirable, **Option 1** (run `migrate deploy` against the current Neon DB from a local machine) is the lower-effort path and is expected to succeed given the IF NOT EXISTS guards.

**Why not run `migrate deploy` now:** This investigation is read-only per the mandate. The deploy must be executed by the owner from a network-enabled environment (local machine or authorized pipeline) with explicit intent and a backup/snapshot in place.
