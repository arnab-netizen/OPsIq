1. CURRENT SPEC

Domain Purpose:
  Governed business intervention and consulting operating system. Must model four dimensions
  at all times: consulting lifecycle stage, business condition, intervention mode/phase,
  human execution reality.

Current Application:
  Backend API service layer for complete intervention workflow from shock detection through
  KPI tracking. Full schema, service layer, API endpoints, and audit event infrastructure.
  No UI for intervention workflow. No end-to-end testing of API layer.

Major Entities:
  User, Session, Role, EngagementMembership
  Lead, ClientAccount, ClientContact
  Engagement, BusinessConditionProfile
  InterventionState, ShockEvent
  EvidenceItem, Finding, FindingEvidenceLink
  Recommendation, Action, KPI, KPIEvent
  AuditEvent, IdempotencyRecord, ScheduledTask

Workflow Supported:
  Engagement creation → BusinessCondition profiling → InterventionState initialization
  → ShockEvent recording → EvidenceItem collection → Finding creation → Recommendation
  generation → Action creation → Action ownership assignment → Action deadline/priority
  setting → KPI baseline/target definition → KPI value changes recorded with attribution
  to actions. InterventionState phase transitions gated at each step. Phase CLOSED blocks
  all writes.

  System admin, user mgmt, role assignment
  Client account CRUD
  Lead CRUD
  Engagement CRUD with member management
  Evidence submission/validation (EVIDENCE_VIEW, EVIDENCE_SUBMIT)

  KPI creation/update (INTERVENTION_MANAGE, INTERVENTION_VIEW)
  BusinessCondition assessment/view
  InterventionState transition control

P0: Re-Evaluation Service Unimplemented
  Risk Level: CRITICAL
  Description: CLAUDE.md mandates that "every significant change must route into governed re-evaluation"
               of BusinessCondition, InterventionMode, InterventionPhase, priority, cadence, health.
               Service exists as stub (logs + emits audit). Never actually re-evaluates anything.
               No triggers from shock, evidence, finding, recommendation, action, KPI, kpi-event.
  Impact: Business logic correctness completely bypassed. Phase/mode/condition never updated
          based on evidence changes, KPI deterioration, failed actions. Engagement stuck in
          stale state indefinitely.
  Trigger: Any shock event, evidence, finding, recommendation, action, or KPI change.
  Blast Radius: Entire intervention workflow.
  Proof of Risk: grep -r "triggerReEvaluation" src/services/ shows 0 calls from intervention modules.

P0: API Routes Untested (All 22 Endpoints)
  Risk Level: CRITICAL
  Description: Zero API route tests. Unknown if routes:
               - Validate input correctly
               - Enforce authentication/capabilities
               - Return correct status codes (200/201/400/404)
               - Emit audit events correctly
               - Enforce phase gating
               - Validate cross-engagement ownership
               - Handle errors (NotFoundError → 404, ValidationError → 400)
  Impact: API may expose data cross-engagements, accept invalid input, silently fail,
          return wrong status codes, omit audit events.
  Proof of Risk: find /home/user/OPsIq/src/app/api -name "*.test.ts" | wc -l = 0

P0: No Delete Path for Corrections
  Risk Level: HIGH
  Description: No DELETE endpoints for shock, evidence, finding, recommendation, action, KPI.
               Cannot remove duplicates, invalid entries, corrections.
  Impact: Duplicate shocks recorded → duplicate findings created → duplicate recommendations
          generated → duplicate actions assigned. Auditors see contradictory records.
          Cannot undo mistakes.
  Trigger: Any user error or duplicate submission (idempotency not enforced).
  Workaround: None. Data persists forever.

P1: Action.recommendationId @unique Constraint
  Risk Level: HIGH
  Description: Schema: recommendationId @unique on Action. Only one action per recommendation ever.
               If action is deleted (not possible), or fails, cannot create another action for same recommendation.
               Violates business logic: one recommendation may need multiple action attempts.
  Current Behavior: Cannot enforce without DELETE. Creates orphan recommendations with no action.
  Impact: Incomplete workflow. Recommendation has no corresponding action execution path.

P1: Duplicate Action Creation (No Idempotency)
  Risk Level: HIGH
  Description: IdempotencyRecord model exists but never used. POST /actions not idempotent.
               Network retry, user double-click, browser refresh → duplicate actions created.
  Impact: Multiple actions for same recommendation (violates @unique constraint) OR
          first action created, second rejected (confusing error), user retries, eventually succeeds
          (but sees error in logs/audit).
  Trigger: Network latency on POST /actions.
  Proof of Risk: No idempotency key validation in API routes. No idempotency key storage in services.

P1: Stale KPI Status After Phase Change
  Risk Level: MEDIUM
  Description: KPI.status derived when currentValue changes. But status not recomputed when:
               - InterventionPhase changes (→ potentially phase-dependent success criteria)
               - BusinessCondition changes (→ KPI baseline/target changes)
               - Engagement scope changes
  Impact: KPI shows "improving" but engagement condition degraded. "target_met" but intervention
          phase reverted to assessment.
  Trigger: Phase or condition change while KPI status is in flux.

P1: Audit Trail Gaps Prevent Reconstruction
  Risk Level: MEDIUM
  Description: Missing previous/new values in audit payloads:
               - ACTION_CREATED missing engagement context
               - KPI_CHANGE_RECORDED missing actor if auto-triggered
               - SHOCK_EVENT_RECORDED missing root cause
               - EVIDENCE_SUBMITTED never emitted (only VALIDATED/REJECTED)
               - FINDING_LINKED never emitted (links created silent)
  Impact: Cannot reconstruct decision tree. Why was action created for this recommendation?
          Who approved the evidence link? Did shock trigger phase change? Unknown.
  Proof: grep "EVIDENCE_SUBMITTED\|FINDING_LINKED\|ACTION_OVERDUE\|KPI_DETERIORATED" src/services/*.ts
         shows 0 emissions (except definitions in constants).

P1: Cross-Engagement Access Not Read-Protected
  Risk Level: MEDIUM
  Description: Phase CLOSED blocks writes but not reads. User can still query completed engagement
               KPIs, recommendations, actions even after phase transitions to handover/closed.
               Can see stale data from archived engagement.
  Impact: Confusion about what's current vs archived. Possible misuse of outdated recommendations.
  Trigger: Phase transition while user still has session.

P1: Concurrent Assignment Race Condition
  Risk Level: MEDIUM
  Description: No locking on assignOwner. Two users simultaneously assign action owner.
               Both read currentValue A, both update to user2/user3. Race condition.
               Last write wins. One assignment silently lost.
  Impact: Action owner ambiguous. One user thinks they're assigned, another user assigned later
          overwrites without knowledge. No audit of lost assignment.
  Trigger: Simultaneous action assign requests.

P1: Evidence-Finding Link Has No Constraints
  Risk Level: MEDIUM
  Description: FindingEvidenceLink.create has @unique([findingId, evidenceItemId]) but no
               validation that evidence belongs to same engagement as finding.
               Can link evidence from engagement A to finding in engagement B.
  Impact: Cross-engagement data contamination. Finding in engagement A now includes evidence
          from engagement B. Audit trail murky.
  Trigger: API call with cross-engagement findingId + evidenceItemId.
  Proof: No cross-engagement validation in evidence-item or finding services when linking.
